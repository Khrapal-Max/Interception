# Аналіз шляхів інтеграції: запуск Interception з USB-носія на ПК

## 1) Поточний стан проєкту (що впливає на запуск з флешки)

На основі коду і конфігурацій:

- Це **ASP.NET Core Blazor Server** застосунок (`Microsoft.NET.Sdk.Web`) на `net10.0` + `LangVersion=preview`.
- База даних — **PostgreSQL** через `Npgsql.EntityFrameworkCore.PostgreSQL`.
- У `Program.cs` рядок підключення береться з `ConnectionStrings:DefaultConnection`.
- Ключі Data Protection зберігаються у файловій системі за абсолютним шляхом `/data-protection-keys`.
- Для деплою вже підготовлений `docker-compose.yml` з сервісами `interception.ui`, `postgres`, `pgadmin`.

Висновок: проєкт сьогодні орієнтований на **контейнерний запуск**, а не на «просто подвійний клік з флешки».

---

## 2) Що означає «працювати з флешки на ПК» — 3 реалістичні моделі

### Модель A — Portable Docker stack (мінімум змін у коді)

**Ідея:** на ПК має бути Docker Desktop; з флешки запускається `docker compose up -d`.

**Плюси:**
- мінімум змін у застосунку;
- найближче до поточного прод-оточення;
- передбачувана поведінка між різними ПК.

**Мінуси:**
- залежність від встановленого Docker (часто недоступно на корпоративних ПК);
- потрібні права/віртуалізація;
- холодний старт повільніший.

**Коли обирати:** якщо цільові ПК контрольовані й Docker гарантовано доступний.

---

### Модель B — Native portable .NET + локальна БД (рекомендовано)

**Ідея:** публікуємо self-contained застосунок під Windows x64 та кладемо поряд локальну БД (краще SQLite, ніж локальний PostgreSQL).

**Плюси:**
- працює без Docker;
- простий запуск через `.bat`/`.ps1`;
- значно менше залежностей на ПК.

**Мінуси:**
- потрібна адаптація під інший провайдер БД (SQLite) або постачання portable PostgreSQL;
- треба продумати конкурентний доступ до файлу БД.

**Коли обирати:** для польового/офлайн сценарію і запуску на «чужих» ПК.

---

### Модель C — Повна зміна технології UI (WPF/WinUI)

**Ідея:** переписати фронт з Blazor Server на desktop UI.

**Плюси:**
- краща desktop-ергономіка;
- нативна інтеграція з ОС.

**Мінуси:**
- найбільша вартість/ризик;
- міграція всього UI і частини бізнес-логіки;
- довгий time-to-market.

**Коли обирати:** тільки якщо є довгострокова стратегія desktop-first на роки вперед.

---

## 3) Інфраструктурні вимоги для запуску з флешки

Незалежно від моделі, потрібно:

1. **Стандартизований launcher** (наприклад `Start-Interception.ps1`):
   - перевірка порту;
   - старт сервісу;
   - відкриття браузера на `http://localhost:8080`.
2. **Portable конфіг** поруч із застосунком:
   - `appsettings.Production.json` або `.env`;
   - окремий профіль `Portable`.
3. **Локальне сховище даних і ключів** на флешці:
   - `./data/` для БД;
   - `./data-protection-keys/` для ключів шифрування.
4. **Логи/діагностика**:
   - `./logs/`;
   - команда/скрипт для збору support bundle.
5. **Резервне копіювання**:
   - кнопка/скрипт `Backup` (zip БД + конфіг + ключі).

## 4) Критичні технічні доопрацювання в поточному коді

### 4.1. Перенести шлях Data Protection у конфіг
Зараз жорстко прописано `/data-protection-keys`, що добре для Docker/Linux, але погано для Windows/USB.

Потрібно:
- винести шлях у конфіг (`Security:DataProtectionPath`);
- якщо не задано — брати шлях відносно `AppContext.BaseDirectory`.

### 4.2. Підтримати подвійний провайдер БД
- `PostgreSQL` для серверного/контейнерного режиму;
- `SQLite` для portable USB-режиму.

Потрібен перемикач у конфігу (`Database:Provider = Postgres|Sqlite`) і окремі рядки підключення.

### 4.3. Спрощений bootstrap міграцій
Зараз міграції викликаються на старті (`AddMigrationDb`). Для portable-режиму важливо:
- чітке логування причин невдачі;
- «м’який» recovery-потік (помилка -> інструкція користувачу).

### 4.4. Стабільна збірка
Проєкт на `net10.0` + `preview` може бути чутливим до оточення. Для польового запуску бажано:
- фіксована версія SDK у `global.json`;
- reproducible publish-скрипт.

## 5) Рекомендована дорожня карта

### Етап 1 (1–2 тижні): Portable без зміни UI
- додати режим `Portable`;
- параметризувати шляхи ключів/логів/БД;
- додати SQLite-провайдер;
- зробити `publish` + launcher для USB.

**Результат:** робочий офлайн-стенд без Docker.

### Етап 2 (1 тиждень): Операційна надійність
- backup/restore;
- health-check скрипт;
- smoke-test на «чистому» Windows ПК.

### Етап 3 (опційно): Product hardening
- шифрування конфіденційних локальних даних;
- цифровий підпис збірки;
- auto-update механізм.

### Етап 4 (стратегічно, 2–4+ місяці): оцінка WPF/WinUI
Робити лише після стабілізації portable-режиму та підтвердження бізнес-потреби.

---

## 6) Вибір технології: залишатися на Blazor чи переходити на WPF

### Коротка рекомендація
**Зараз не переходити на WPF.**

Спочатку зробити portable-архітектуру в межах поточного Blazor Server + SQLite. Це дасть найшвидший time-to-value з контрольованими ризиками.

### Коли міграція на WPF виправдана
- потрібні глибокі desktop-фічі (драйвери, COM, нативні інтеграції);
- критичний UX без браузера;
- довгий горизонт підтримки саме desktop-каналу.

## 7) Мінімальний чекліст готовності USB-рішення

- [ ] Запуск на Windows 10/11 без інсталяції додаткового ПЗ.
- [ ] Дані і ключі повністю зберігаються на флешці.
- [ ] Є backup/restore у 1 клік.
- [ ] Час старту <= 30–60 сек на типовому ПК.
- [ ] Працює офлайн, без доступу до інтернету.
- [ ] Є інструкція для користувача (1 сторінка).

---

## 8) Практичний висновок

Найкращий компроміс для вашої задачі зараз:

1. **Не міняти Blazor на WPF на першому кроці.**
2. **Додати portable-режим + SQLite + параметризовані шляхи.**
3. **Пакувати self-contained release на USB з launcher-скриптом.**

Це дозволить швидко отримати працездатний сценарій «запуск з флешки на ПК» з мінімальним ризиком і без великого переписування системи.
