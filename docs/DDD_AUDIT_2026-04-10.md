# Потворний DDD-аудит проєкту Interception

_Дата: 10 квітня 2026_

## 1) Executive summary

- **Загальна оцінка відповідності DDD:** **8.1 / 10**.
- **Сильна сторона:** доменні інваріанти реально живуть у сутностях (`InterceptionMessage`, `ParticipantCandidateGroup`, `CanonicalPerson`).
- **Слабке місце:** аналітичний use case (`ParticipantCandidateAnalysisService`) все ще містить багато доменного прийняття рішень у Application-шарі.
- **Ризик архітектури:** спільний `AppDbContext` для кількох контекстів підвищує coupling bounded contexts.

## 2) Що вже добре по DDD

### 2.1 Bounded contexts явно проговорені в документації

- У проєкті вже описані контексти: `Interceptions`, `Registry`, `Analytics`, `Reports`, `Import/Export`.
- Це свідчить, що команда мислить не таблицями БД, а domain-межами.

### 2.2 Інваріанти сидять у Domain, а не в UI

- `InterceptionMessage` гарантує унікальність відомого учасника в межах повідомлення.
- Там же обробляється унікальність міток і нормалізація значень.
- Це правильна tactical DDD-практика: aggregate root контролює консистентність.

### 2.3 Aggregate behavior є, і воно не "порожнє"

- `ParticipantCandidateGroup` має поведінку станів (`Open -> Confirmed/Dismissed`) і забороняє невалідні зміни через `EnsureOpen`.
- `CanonicalPerson` блокує дублювання member-ів та тримає update-правила всередині root.
- `TopologySnapshotRun` має явні transition-методи (`Complete`, `Fail`, `MarkStale`) замість зовнішнього мутабельного set-стилю.

### 2.4 Є архітектурні тести меж шарів

- Тести перевіряють, що `Components` не залежить напряму від `Domain`/`Infrastructure`.
- Додатково зафіксовано, що `Domain` не тягне `Application`/`Components`.
- Це хороший fitness-function для підтримки clean boundaries.

## 3) Де болить (і чому це DDD-борг)

### 3.1 Application-сервіси місцями занадто "розумні"

`ParticipantCandidateAnalysisService` містить великий обсяг рішень, які за змістом доменні:
- відбір кандидатів;
- умови приєднання до open-group;
- правила формування нових груп;
- перерахунок оцінок і причин.

Частина логіки вже винесена в policy (`ParticipantCandidateGroupingPolicy`) і math helper, але orchestration все ще перевантажений доменною семантикою. Це ознака неповного переходу до rich domain model.

### 3.2 Cross-context coupling через єдиний AppDbContext

`AppDbContext` включає сутності з різних контекстів одночасно (Interceptions/Analytics/Reports/Topology/Registry). Це практично для швидкої розробки, але:
- ускладнює незалежну еволюцію контекстів;
- робить границі транзакцій неочевидними;
- підвищує ризик витоку моделей між контекстами.

### 3.3 Часткова VO-уніфікація

У write-side для `InterceptionCommandService` уже використано `PersonName`, `FrequencyCode`, `DivisionName`, що добре.
Але в окремих доменних методах все ще переважають сирі `string` та ручна нормалізація. Це збільшує ризик роз'їзду інваріантів у майбутньому.

## 4) Bounded context maturity (коротка матриця)

| Context | Maturity | Коментар |
|---|---:|---|
| Interceptions | 8.8 | Сильний aggregate + інваріанти + чистий command flow |
| Registry | 7.8 | Фактично supporting контекст; потрібні суворіші контракти еволюції |
| Analytics | 7.2 | Потужний функціонально, але частина domain decisions живе в app services |
| Reports | 8.0 | Нормальний downstream read-side без зайвих command-обов'язків |
| Import/Export | 7.6 | Коректний integration layer, потрібне системне contract testing |

## 5) Пріоритетні кроки (R3 -> R4)

### P1 (критично)
1. Винести правила групування unknown participants у domain service/specification набір (не лише policy-checks).
2. Формалізувати доменні події для `ParticipantCandidateGroup` (Created/Enriched/Confirmed/Dismissed) і перейти з "після-save процедур" до event-driven orchestration.
3. Для ключових міжконтекстних DTO додати contract tests (approval/snapshot).

### P2 (важливо)
1. Розділити persistence-межі: хоча б логічно (окремі DbContext read/write або по контекстах) без форсованого physical split на старті.
2. Посилити Value Objects для роль/назва/частота/підрозділ у всіх write use cases.
3. Уніфікувати помилки домену в typed-domain-exceptions, щоб application шар не парсив текстові помилки.

### P3 (еволюційно)
1. Ввести lightweight ADR для кожного bounded context (owner, ubiquitous language, invariants).
2. Додати метрики архітектури (кількість forbidden dependencies, coupling index між контекстами).

## 6) Висновок

Проєкт уже **вище середнього** за DDD-зрілістю: у ньому є реальні aggregate roots, інваріанти та архітектурні тести меж.
Головний next step — **дотиснути Analytics до domain-first стилю** і зменшити coupling від shared persistence.

Якщо коротко: фундамент правильний, тепер час «докрутити» стратегічний DDD (контракти, події, межі контекстів), щоб масштабування не зламало модель.
