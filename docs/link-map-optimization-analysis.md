# Аналіз оптимізації `analytics/link-map`

## Контекст поточної логіки

У поточній реалізації `LinkMapService` пайплайн такий:

1. Будується мапа `frequency -> dominant division`.
2. Формуються комунікаційні групи на базі частоти та графа співзустрічей учасників.
3. Для групи визначається центральна особа (`KeyPerson`) за топологічними ознаками.
4. Після цього рахуються міжгрупові мости (`bridges`) між центрами/ядрами груп.

Тобто сервіс добре показує структуру зв'язків, але не дає явного діагностичного шару:
- чи підрозділ підтверджений/виведений/відсутній;
- які особи мають неповні картки (роль, підрозділ);
- які поля потенційно можна автозаповнити з прийнятною довірою.

## Що саме потрібно додати для вашої задачі

Щоб відповісти на питання:
- «чи можна визначити підрозділ, якщо в повідомленні підрозділ порожній?»;
- «хто з людей має неповні дані?»;
- «що можна заповнити автоматично?»

потрібен окремий **шар діагностики якості даних** поверх `link-map`.

## Пропонована модель діагностики (мінімально необхідна)

### 1) Статус підрозділу групи

Для кожної групи виводити:

- `DivisionStatus = Confirmed`
  - у групи є валідний підрозділ із прямого спостереження.
- `DivisionStatus = InferredByFrequency`
  - підрозділ не був у частині повідомлень, але стабільно відновився через `frequency -> division`.
- `DivisionStatus = Missing`
  - підрозділ не вдалося визначити (ані явно, ані через частоту).
- `DivisionStatus = Ambiguous`
  - є 2+ конкурентні підрозділи з близькою вагою, без явного лідера.

### 2) Статус повноти по учаснику

Для кожного `MemberDetails` додати:

- `ProfileCompleteness` (0..100), де
  - +40 за наявне ім'я,
  - +30 за роль,
  - +30 за підрозділ (прямий або inferred).
- `MissingFields` (`Role`, `Division` тощо).
- `DivisionSource` (`Direct`, `InferredByFrequency`, `InferredByGroup`, `Missing`).
- `AutoFillCandidate` (`true/false`) — чи можна безпечно запропонувати автозаповнення.

### 3) Рекомендація для оператора

Додати текстову підказку на UI:
- `"Заповнити підрозділ: 336 мсп (довіра 0.78, 14 згадок)"`;
- `"Потрібна ручна валідація: 336 мсп vs 15 омсбр (0.44 / 0.41)"`.

## Як визначати підрозділ, якщо він відсутній

Використати багатосигнальний скоринг (щоб не покладатися лише на частоту):

`Score(division) = 0.50 * FreqSignal + 0.30 * GroupSignal + 0.20 * BridgeSignal`

де:

- `FreqSignal` — частка згадок підрозділу на частотах конкретної особи;
- `GroupSignal` — домінантний підрозділ у поточній стабільній групі;
- `BridgeSignal` — підрозділи сусідніх груп із сильними мостами.

Правило прийняття:

- якщо `bestScore >= 0.65` і `bestScore - secondScore >= 0.15` → `Inferred`;
- інакше → `Ambiguous` або `Missing`.

Це знімає проблему, коли «підрозділ може бути відсутній за частотою»: тоді вирішують `GroupSignal` і `BridgeSignal`.

## Як знайти «пусті» вузли прямо зараз

Навіть без змін моделі можна одразу показати технічні маркери:

1. **Пустий підрозділ групи:** `group.Division == null`.
2. **Пуста роль учасника:** `member.Role == null`.
3. **Низька надійність групи:** мало згадок + мало унікальних партнерів.
4. **Потенційно заповнюваний кейс:**
   - у особи `Division == null`,
   - але у її частот є стабільний `frequency -> division`.

## Пропозиція по UI (`/analytics/link-map`)

Додати в лівий список і в drawer групи:

- бейдж `DivisionStatus`;
- індикатор якості `Data Quality: 0..100`;
- лічильник `Missing people: N`;
- кнопку/фільтр `Показати лише неповні`.

Для таблиці взаємодій:

- колонка `Якість цільової групи`;
- колонка `Рекомендоване заповнення`.

## Очікуваний ефект

Після цих змін карта зв'язків стане не лише «картинкою зв'язків», а й інструментом управління якістю даних:

- видно, де саме прогалини (група/особа);
- видно, що саме можна заповнити автоматично;
- видно, де потрібна ручна перевірка через неоднозначність.
