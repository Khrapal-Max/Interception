# Аналіз можливості створення аналітичного звіту по особах і підрозділах (pivot)

## 1) Висновок коротко

Реалізація **можлива без змін доменної моделі**: у поточній БД вже є дані, достатні для звіту
«особа → підрозділ» з контролем умови **«назва особи є, підрозділ відсутній»**.

Ключова ідея: для осіб без підтвердженого підрозділу застосувати **pivot-перетин**:

- вісь A: `особа × частота` (з повідомлень/груп кандидатів);
- вісь B: `частота × підрозділ` (домінуючий підрозділ по частоті);
- перетин: через частоту отримати найімовірніший підрозділ для особи.

## 2) Що вже є в проєкті і може бути повторно використано

У сервісі `DivisionReportService` вже реалізовані потрібні механізми:

1. Побудова мапи `frequency -> dominant division` (`BuildFrequencyDivisionMap`).
2. Визначення `effective division` для повідомлення (`ResolveEffectiveDivision`) з fallback по частоті.
3. Логіка «домінуючого підрозділу» для сутностей, що мають кілька згадок.

Це майже той самий підхід, який потрібен для pivot-звіту по особах.

## 3) Цільовий формат звіту

Рекомендований формат рядка:

- `PersonName`
- `ConfirmedDivision` (якщо є у реєстрі осіб)
- `PivotDivision` (обчислений через частоти)
- `DivisionStatus`:
  - `Confirmed`
  - `InferredByPivot`
  - `Missing` (немає надійного перетину)
- `TopFrequencies` (топ-N частот особи)
- `Confidence` (0..1)
- `LastSeenAt`

Фільтр за вимогою:

- показувати лише записи, де `PersonName` не порожній і `ConfirmedDivision` відсутній;
- додатково (опційно): тільки `Missing` або тільки `InferredByPivot`.

## 4) Pivot-алгоритм (пропозиція)

1. **База повідомлень** за датою/періодом.
2. Побудувати довідник `frequency -> division`:
   - брати лише «змістовні» підрозділи;
   - для кожної частоти обрати домінуючий підрозділ за кількістю згадок.
3. Зібрати зв’язки `person -> [frequencies]`:
   - з `InterceptionMessage.Participants` (не unknown);
   - за бажанням доповнювати через `ParticipantCandidateGroup`.
4. Для осіб без `ConfirmedDivision`:
   - по кожній її частоті підставити `division` із довідника;
   - агрегувати у розрізі `division` (рахунок, вага, остання дата);
   - взяти переможця за правилом: `max(count)`, потім `max(lastSeenAt)`.
5. Розрахувати `Confidence`:
   - базово: `votes_winner / votes_total`;
   - поріг, напр. `>= 0.6` для статусу `InferredByPivot`, інакше `Missing`.

## 5) Практичний план впровадження

### Етап 1 (MVP)

- Створити `IPersonDivisionPivotReportService` + DTO для рядків.
- Реалізувати сервіс на основі існуючих helper-підходів з `DivisionReportService`.
- Додати сторінку в UI розділу Reports з таблицею і фільтрами:
  - період,
  - статус (`Missing`, `InferredByPivot`, `All`),
  - мінімальний confidence.

### Етап 2

- Експорт CSV/Excel.
- Показ «пояснення»: які саме частоти сформували `PivotDivision`.
- Підсвічування конфліктів (коли 2+ підрозділи з близькою вагою).

## 6) Ризики та обмеження

- Частота може використовуватись кількома підрозділами у різні дні/зміни.
- Дані можуть бути шумними (епізодичні згадки, помилки оператора).
- Потрібно обмежувати період (наприклад, останні 7/30 діб), щоб не змішувати історичні контексти.

## 7) Критерії приймання (DoD)

1. Звіт повертає всі записи, де `PersonName` є, а `ConfirmedDivision` відсутній.
2. Для кожного такого запису є або `PivotDivision`, або статус `Missing`.
3. Для `PivotDivision` відображається confidence та щонайменше 1 supporting frequency.
4. Результати стабільні при повторному запуску на однаковому зрізі даних.

## 8) Оцінка трудовитрат

- MVP: 1-2 робочі дні (service + UI table + базові фільтри).
- Повний варіант з експортом і поясненням причин: 2-4 дні.

---

**Підсумок:** технічно задача добре лягає на наявну архітектуру; pivot-перетини
`person × frequency × division` можна реалізувати як окремий звіт із мінімальними ризиками.
