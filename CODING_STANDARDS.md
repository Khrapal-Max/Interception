# CODING STANDARDS

## 1. Мета документа

Цей документ фіксує стандарти написання коду для проєкту **Interception.UI** та суміжних модулів.

Принцип простий:

- спочатку **простий робочий каркас**
- потім **перевірка через тести / реальний сценарій**
- лише після цього **рефакторинг і покращення**

---

## 2. Загальні принципи

1. Писати **простий, читабельний код**.
2. Не ускладнювати рішення без реальної потреби.
3. Не створювати нові абстракції, helper-и, record-и, DTO чи сервіси, якщо задачу можна вирішити поточними засобами.
4. Не робити “магічну” логіку там, де потрібна прозора і керована поведінка.
5. Новий код має виглядати так, ніби він **завжди був частиною проєкту**.

---

## 3. Пріоритети при реалізації

Пріоритети завжди такі:

1. **Сумісність з поточною архітектурою проєкту**
2. **Простота**
3. **Читабельність**
4. **TDD / перевірюваність**
5. **Акуратний рефакторинг після робочого варіанту**
6. **Оптимізація лише коли вона справді потрібна**

---

## 4. Архітектурні правила

### 4.1 UI

- UI **не повинен працювати з Domain напряму**.
- UI працює через `Application` сервіси, DTO, read-model або спеціальні service-model.
- Для сторінок Blazor використовуємо **окремий code-behind** (`.razor` + `.razor.cs`), якщо сторінка не зовсім тривіальна.
- Для drawer/modal використовуємо **існуючі shared-патерни** проєкту.

### 4.2 Application

- `Application` є шаром координації сценарію.
- `Application` може працювати з Domain, репозиторіями, сервісами, DTO.
- Хендлери та сервіси мають повертати дані в формі, зручній для UI.
- Якщо для задачі достатньо простого сервісу, не потрібно вигадувати додатковий orchestration layer.

### 4.3 Domain

- Domain не тягнемо в UI.
- Не додаємо в UI залежність від доменних enum/const, якщо вже є application DTO або UI-friendly модель.
- Domain змінюємо тільки коли цього справді вимагає бізнес-логіка, а не зручність конкретної сторінки.

### 4.4 Repository / Infrastructure

- Не змінювати контракти репозиторіїв без чіткої потреби.
- Репозиторій повертає те, що вже прийнято архітектурою: агрегат, сутність або read-model.
- Не прошивати UI-логіку в repository.

---

## 5. Стиль реалізації коду

### 5.1 Загальний стиль

- Починати з **простого каркасу**.
- Якщо задачу можна вирішити трьома зрозумілими функціями — так і робити.
- Уникати зайвих проміжних shape-model / snapshot / projection-type, якщо вони не дають явної користі.
- Не розбивати логіку на багато дрібних класів “про запас”.

### 5.2 Що не робити без окремого запиту

- не створювати нові abstraction/interface “на майбутнє”
- не додавати нові локальні record-и для внутрішньої зручності, якщо можна обійтись без них
- не виносити helper-и в окремі сервіси без повторного використання
- не робити “розумні” універсальні рішення там, де потрібна проста бізнес-логіка

### 5.3 Naming

- Назви мають бути прямими, зрозумілими і предметними.
- Якщо в проєкті вже є усталений неймінг — новий код має його продовжувати.
- Не вводити нові терміни для вже існуючих понять.

---

## 6. Стандарти для Blazor UI

### 6.1 Дизайн

- Основа UI — **Bootstrap-first**.
- Існуючі стилі проєкту мають пріоритет над новими.
- **Не змінювати CSS**, якщо цього прямо не просили.
- Не додавати нові стилі, якщо задачу можна вирішити наявними Bootstrap-класами та існуючими класами проєкту.

### 6.2 Сторінки

- Орієнтуватися на вже існуючі сторінки як на еталон.
- Відступи, toolbar, page-panel, table-wrap, data-table, drawer layout — використовувати у вже прийнятому стилі.
- Якщо користувач дає еталонну сторінку, нову сторінку треба будувати **в її ритмі**, а не “з нуля по-своєму”.

### 6.3 Drawer / Modal

- Використовувати shared drawer / modal патерни проєкту.
- Не змішувати в одному drawer різні рівні дії, якщо вони відрізняються по наслідках.
- Локальна правка і глобальне злиття/перебудова — це різні сценарії.

---

## 7. Робота з датою і часом

1. У проєкті БД використовує `timestamp with time zone` (`timestamptz`).
2. Для запису в БД потрібно передавати **UTC**.
3. Для UI використовувати наявні extension/helper-и проєкту.
4. Якщо це **datetime-local**, працювати через відповідний converter/extension.
5. Якщо це **date-only фільтр**, не змішувати його з логікою `datetime-local`.
6. Для запитів по періоду віддавати перевагу інтервалу:
   - `>= from`
   - `< toExclusive`

---

## 8. Робота з EF Core

### 8.1 Загальні правила

- Писати **прості EF-запити**.
- Не робити зайвих складних projection, якщо можна прочитати дані простіше.
- Не вводити нові проміжні моделі лише для того, щоб “гарніше зібрати LINQ”.
- Якщо логіку простіше завершити в пам’яті після читання необхідного набору даних — це допустимо, якщо обсяг нормальний.

### 8.2 Обережність

- Уникати не-трансльованих LINQ-виразів без потреби.
- Пам’ятати, що `DateTime Kind` важливий для PostgreSQL/Npgsql.
- Не використовувати складні вирази, якщо їх важко перевірити і супроводжувати.

---

## 9. TDD і тести

### 9.1 Основне правило

- Якщо задача йде через TDD, то порядок такий:
  1. оновити/написати тести
  2. отримати зрозумілий контракт
  3. написати мінімальну реалізацію
  4. лише потім рефакторити

### 9.2 Принцип тестів

- Тести мають перевіряти **бізнес-поведінку**, а не випадкову структуру коду.
- Не потрібно ускладнювати реалізацію “заради красивого тесту”.
- Якщо вже є прийнятий стиль тестів у проєкті — нові тести мають його наслідувати.

### 9.3 Для UI тестів

- Дотримуватись патерну, який уже є в проєкті.
- Не вигадувати інший стиль біндінгу, drawer interaction чи toast verification, якщо в рішенні вже є стандарт.

---

## 10. Документація в коді

- Публічні класи, сервіси, DTO, сторінки, важливі методи — документувати.
- XML-коментарі писати **українською мовою**.
- Коментарі мають пояснювати **роль і намір**, а не дублювати код.

---

## 11. Як робити patch

Patch повинен бути:

- **точковим**
- без зайвих сторонніх змін
- без випадкового рефакторингу всього навколо
- без зміни стилів/архітектури, якщо це не потрібно для задачі

Якщо змінюється UI-сторінка, не потрібно паралельно “покращувати” інші місця без запиту.

---

## 12. Антипатерни для цього проєкту

У цьому проєкті **небажано**:

1. вигадувати нові helper-model / projection-record без потреби
2. додавати нові CSS-класи замість використання наявного стилю
3. змішувати локальну правку запису і глобальну корекцію сутності в один сценарій
4. робити автоматичні глобальні виправлення без підтвердження користувача
5. міняти дизайн сторінки без прямого запиту
6. тягнути Domain у UI
7. ламати існуючий ритм сторінок “бо так красивіше”
8. робити складну архітектуру там, де вистачає простого сервісу

---

## 13. Продуктове правило для звітів і коригувань

- Звіт показує наслідок поточного стану даних.
- Звіт не повинен “магічно лікувати” помилки у вихідних даних.
- Якщо у звіті видно дубль/помилку — потрібно відкривати сценарій коригування джерельних записів або канонічної особи.
- Локальне редагування і глобальне об’єднання — окремі дії.

---

## 14. Еталонний підхід до реалізації

За замовчуванням очікується такий порядок:

1. зрозуміти поточний стиль проєкту
2. взяти існуючий еталонний файл/сторінку
3. написати **простий каркас**
4. перевірити через TDD або реальний сценарій
5. зробити мінімальний рефакторинг
6. не виходити за межі задачі
7. поставити примітки XML

---

## 15. Якщо є сумнів

Якщо є кілька варіантів реалізації, пріоритет такий:

- той, що **менше ламає поточний стиль проєкту**
- той, що **простішій для читання**
- той, що **легше тестувати**
- той, що **не створює зайвих нових сутностей**

---

## 16. Коротка формула проєкту

> TDD завжди перший. 
> Простий каркас.  
> Примітки XML
> Bootstrap-first.  
> Без зайвої магії.  
> Без зайвих абстракцій.  
> У стилі вже існуючого проєкту.
